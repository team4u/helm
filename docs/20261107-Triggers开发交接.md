# builtin:triggers 开发交接

`builtin:triggers` 是第四个内置插件：`cron` 与 `webhook` 两个入站连接器，把外部事件经 `defang` 防逃逸信封投入内核 `trigger` 管道。本文档覆盖启用方式、动作字段、webhook 签名与 curl 示例、cron 交付语义、secret 边界与真实实现边界，供使用与验收对照。

实现由并行代理交付（`createTriggersPlugin` + `createHelm` 默认 `enabled:false` 注册），本文档与 `packages/kernel/test/triggers.test.ts`、`packages/node/test/triggers-cli.test.ts` 同契约编写。集成状态以主代理验收记录为准。

## 启用与停用

插件默认停用注册，显式启用后动作、路由与公开 doc 才可用；开关写入 `config.json.pluginEnabled`，重启沿用。

```bash
pnpm helm plugins enable builtin:triggers --json
pnpm helm plugins list --json
```

停用后 `cron`/`webhook` 动作显式拒绝（`plugin_disabled`），webhook 路由 404，公开 doc 404。停用不会删除已配置的任务与 webhook 元数据；重新启用后恢复。

## cron 任务

### 字段

`cron_create` 输入（必填 `id`、`schedule`、`text`）：

| 字段 | 类型 | 缺省 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 必填 | 任务唯一标识，重复创建显式 409 |
| `schedule` | string | 必填 | cron 表达式（5 段） |
| `text` | string | 必填 | 事件载荷文本，进入 defang 信封 |
| `description` | string | 无 | 人类可读说明 |
| `timezone` | string | `UTC` | 计算时区，IANA 名称 |
| `enabled` | boolean | `true` | 停用任务不排程 |
| `catchUp` | boolean | `false` | 见交付语义 |
| `targetConversationId` | number | 无 | 显式目标会话，直投 |
| `targetProfileId` | string | 无 | 按 Profile 路由 |
| `threadKey` | string | 无 | 订阅直通键（superagent 可命中直投） |

`targetConversationId` 与 `targetProfileId` 互斥，同时提供显式 400。

任务元数据（`cron_list` 与公开 doc `crons`）包含 `id/schedule/text/timezone/enabled/catchUp`、可选目标字段、`lastRunAt?`（仅真实运行过）、`nextRunAt`（计算字段，可为 null）与 `lastError?`。未运行过的任务不伪造 `lastRunAt`。

### CLI

```bash
pnpm helm cron list --json
pnpm helm cron create --id nightly --schedule '0 3 * * *' --text '请汇总今日工作并汇报' --timezone Asia/Shanghai --json
pnpm helm cron trigger --id nightly --json
pnpm helm cron delete --id nightly --json
```

全部支持 `--input '<JSON>'` 整体提交与 `--json`；`cron list/trigger/delete` 可用 `--current` 携带会话上下文。字段 flag 为 kebab-case（`--catch-up`、`--target-conversation-id`、`--thread-key`）。

### 交付语义（如实声明，不承诺 exactly-once）

- **同一计划点最多尝试一次**：调度器对每个任务按计划点持久 claim，claim 落盘（经 factory 注入的 `flushDocs` 冲刷 `documentStore`）之后才 `dispatchTrigger`。
- **崩溃窗口**：claim 已落盘但 dispatch 之前进程崩溃，该次计划事件可能丢失。这是当前实现的固有权衡，不承诺 exactly-once。
- **catchUp=true**：进程离线期间错过的多个计划点压缩为一次补跑（at-least-once 上限为每计划点一次、补跑合并为一次）。
- **catchUp=false**（缺省）：错过的计划点直接跳过，只面向未来计划点。
- **手动 `cron trigger`**：显式新事件，不是计划补跑，不影响 claim 水位；可重复调用，每次都是独立事件。
- 排程细节（时钟、时区计算、catchUp 合并的专项单测）由 cron 实现代理的测试负责。

### 事件信封

cron 事件源为 `cron:<id>`，经 `host.dispatchTrigger` 进入 trigger 管道；`text` 由内核 `defang` 做 XML 转义包裹（`<external_event ... untrusted="true">`），输入 entry 附着 `origin: 'trigger'`。

## webhook

### 创建与 secret 配置（人工通道）

```bash
pnpm helm webhook create --id ci --secret 'WHSECRET_CI_请随机生成' --description 'CI 回调' --json
pnpm helm webhook list --json
pnpm helm webhook delete --id ci --json
```

- secret 只应经**人工 HTTP/CLI** 配置（`webhook_create` 输入）。不要把原始 secret 交给模型或工作流经 `run_action` 转发——模型上下文与时间线不保证机密性，实现方也可能拒绝携带会话上下文的创建调用。需要模型参与管理时，先由人工创建，再让模型使用不含 secret 的 `cron/webhook list/delete` 等动作。
- secret 落盘 `~/.helm/credentials.json` 的 `pluginSecrets['builtin:triggers']['webhook:<id>']`，文件恒 `0600`，并登记 SecretStash 全局逐值脱敏（任何会话回显该值都会被替换为 `[REDACTED]`）。
- secret 绝不出现在：插件 docs、`state.sqlite` 任何表（含 FTS5）、action 输出、公开 doc、`GET /api/plugins/:id/config` 的 values 输出。
- `webhook_delete` 只删除该 hook 自己的 secret 键，不影响其他 hook。
- `webhook_create` 返回与 `webhook_list`/公开 doc `webhooks` 均为**不含 secret 的元数据**，以 `hasSecret: true` 表达已配置。

### 接收端点与签名

```
POST /api/plugins/builtin%3Atriggers/routes/webhook/<id>
```

- 端点 `public: true`（免 Hub token），验签由插件自行完成。
- 请求头 `x-helm-signature: sha256=<HMAC-SHA256 hex>`，密钥为创建时的 secret，**对原始 body 字节**计算——不是对 JSON 重新序列化后的等价形式。服务器接收原始字节并按 UTF-8 解码为事件文本。
- 结果：验签通过 `202 {"accepted":true}`；无签名或不匹配 `401`；未注册 webhook `404`。

curl 示例（注意用 `--data-binary` 保持字节原样）：

```bash
SECRET='WHSECRET_CI_请随机生成'
BODY='{"event":"build.finished","status":"failed"}'
SIG="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -hex | sed 's/^.* //')"
curl -isS -X POST "http://127.0.0.1:3202/api/plugins/builtin%3Atriggers/routes/webhook/ci" \
  -H "content-type: application/octet-stream" \
  -H "x-helm-signature: $SIG" \
  --data-binary "$BODY"
```

事件源为 `webhook:<id>`，同样经 `dispatchTrigger` + defang 信封 + `origin: 'trigger'` 投递。签名 secret 跨重启从 credentials.json 恢复，重启后旧签名依然有效。

### 目标路由

与 cron 相同的目标字段（`targetConversationId` / `targetProfileId` 互斥、可选 `threadKey`）。缺省目标经 `dispatchTrigger` 走根会话 `#1`；启用 `builtin:superagent` 后由其 trigger hook 路由（静默源优先、有效 threadKey 订阅直投次之、信封已有显式 `targetConversationId` 则尊重直达，其余进中枢）。

## 与 superagent 的协作

- superagent 未启用：缺省目标事件进 `#1`；显式 `targetConversationId` 直投目标会话。
- superagent 启用后：缺省事件改投中枢（`routerConversationId`）；显式目标仍直达，不被覆盖；`threadKey` 命中有效订阅时直投 Worker，订阅失效时回退中枢。`mutedSources`（如 `cron`）可静默丢弃指定源。

## 已知边界与诚实声明

- cron 不是 exactly-once（见交付语义）；claim 后崩溃可能丢一次。
- secret 的进程内边界：SecretStash 防「落盘与模型上下文回显」，不防同进程可信代码（shell、插件）读取——与全仓机密边界口径一致。
- webhook 端点无速率限制与重放防护（时间戳/nonce 未设计）；签名只保证来源持有 secret 与 body 完整性。
- `cron trigger` 手动触发不更新 `lastRunAt` 语义下的计划水位（以实现代理契约为准）。
